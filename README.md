# Практическая работа Observability

API и пакетный источник публикуют задачи в ограниченную очередь RabbitMQ. FastStream-воркер загружает модель из MLflow по alias `champion` и сохраняет результат в PostgreSQL. Дашборд "Конвейер" показывает состояние системы и позволяет перейти от лога задачи к её трейсу.

## Стек и выбор инструментов

Для лабораторной выбраны Loki, Tempo и Prometheus. Стек рассчитан на один Docker-хост, пакет из 6000 задач и хранение данных за два дня. При выборе учитывались ограничение памяти около 1,5 ГиБ, поиск истории отдельной задачи и связь логов, трейсов и метрик в Grafana.

**Логи: Loki.** Основные запросы в работе: ошибки за интервал и история задачи по `task_id` или `trace_id`. Loki позволяет сначала выбрать сервис и временной диапазон, затем отфильтровать JSON-поля. Он индексирует лейблы, поэтому для хранения этих логов не нужен полнотекстовый индекс. Вариант с ELK потребовал бы настройки Elasticsearch, его heap и индексов; для объёма лабораторной такая схема избыточна. VictoriaLogs также подходит, но Loki выбран из-за встроенной поддержки в Grafana и удобной настройки переходов к Tempo. Поиск по ID за широкий интервал требует чтения блоков логов, поэтому запросы ограничиваются временем и сервисом.

**Трейсы: Tempo.** В работе нужен полный путь одной задачи от публикации до записи результата в БД и переходы между трейсом и логами. Tempo имеет встроенный источник данных в Grafana: связь с Loki задаётся в provisioning и восстанавливается вместе со стендом. Jaeger и VictoriaTraces тоже позволяют хранить трейсы, но в выбранной конфигурации Tempo закрывает эту задачу в уже используемом интерфейсе Grafana. Для лабораторной используется один экземпляр с локальным томом и retention 48 часов.

**Метрики: Prometheus.** Он позволяет считать скорость публикации и обработки через `rate`, перцентили по гистограммам через `histogram_quantile` и выполнять правила алертов. Встроенный Prometheus-плагин RabbitMQ предоставляет нужные метрики очередей. При оценке около 240 рядов конвейера и хранении за два дня достаточно одного экземпляра с локальным хранилищем. VictoriaMetrics также подходит, но для этой работы дополнительные возможности длительного хранения не нужны; Prometheus совмещает хранение, PromQL и выполнение алертов в одном сервисе. Метрики приложения принимаются по OTLP через Collector, а RabbitMQ опрашивается напрямую.

Логи собирает Grafana Alloy: он обнаруживает контейнеры по метке Compose-проекта и отправляет их stdout в Loki. Трейсы и метрики приложения отправляются через OpenTelemetry Collector. Grafana объединяет все три сигнала. Конфигурация и дашборд хранятся в репозитории.

Для логирования используется стандартный `logging`: он уже применяется библиотеками, поэтому общий JSON-форматтер задаёт единый формат без дополнительных зависимостей. Логи выводятся в stdout, уровень задаётся через `LOG_LEVEL`. `task_id` добавляется через контекст обработки, а `trace_id` и `span_id` берутся из активного спана. Секреты и входные записи целиком не логируются, успешные health-check имеют уровень `DEBUG`.

В Loki используются только лейблы `service`, `level`, `env`. `task_id` и `trace_id` остаются полями JSON: уникальные идентификаторы создали бы слишком много потоков.

Для метрик приложения выбран push по OTLP: короткоживущий источник может завершиться между опросами, а при штатном завершении SDK отправляет последние значения. RabbitMQ опрашивается через встроенный Prometheus-плагин на порту `15692`. Память процессов измеряется через `psutil`.

## Запуск

Требуются Python 3.12, `uv` и Docker Compose с поддержкой `include` и `configs.content`. Команды для PowerShell выполняются из корня репозитория. Сначала запускается инфраструктура, затем регистрируется демонстрационная модель и запускаются API и воркер. Повторный запуск сохраняет данные.

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
$env:COMPOSE_PROJECT_NAME = 'mlops-observability-demo'
$env:MODEL_URI = 'models:/mlops_observability_demo@champion'
uv sync --locked
docker compose build app mlflow
docker compose --profile observability up -d --wait --wait-timeout 600 postgres rabbitmq mlflow alloy loki otel-collector tempo prometheus grafana
uv run --locked python scripts/demo_observability.py init
docker compose --profile observability up -d --wait --wait-timeout 600
```

Команда `init` регистрирует демонстрационную модель после готовности MLflow. Эта модель возвращает константу 42 и используется для проверки конвейера, ошибок и телеметрии; качество прогноза M5 проверяется отдельно обучаемой моделью. Источники данных и дашборд загружаются из [provisioning](observability/grafana/provisioning), а правила алертов хранятся в [Compose-конфигурации Prometheus](observability/compose.yaml). Вход в [дашборд "Конвейер"](http://localhost:3000/d/mlops-pipeline): пользователь `admin`, пароль `GRAFANA_PASSWORD` из `.env`. Правила доступны в **Alerting > Alert rules > Data source-managed** и в [Prometheus Alerts](http://localhost:9090/alerts).

| Команда | Сервисы наблюдаемости |
| --- | --- |
| `docker compose up -d` | Логи в stdout |
| `docker compose --profile logs up -d` | Alloy и Loki |
| `docker compose --profile traces up -d` | Collector и Tempo |
| `docker compose --profile metrics up -d` | Collector и Prometheus |
| `docker compose --profile observability up -d` | Все сигналы и Grafana |

Источник запускается по запросу через `docker compose run source`. Настройки `OTEL_*`, `LOG_LEVEL` и версии образов приведены в [.env.example](.env.example). При недоступном Collector приложение продолжает обработку. Очереди и повторы фонового экспорта ограничены, поэтому часть сигналов может потеряться. `OTEL_SDK_DISABLED=true` отключает SDK, а `OTEL_TRACES_EXPORTER=none` и `OTEL_METRICS_EXPORTER=none` позволяют выключить отдельный экспорт.

Чтобы проверить provisioning на пустых томах, можно выполнить `docker compose --profile observability --profile tools down -v --remove-orphans` в отдельном тестовом Compose-проекте и повторить запуск по инструкции выше. Команда удаляет БД, модели и телеметрию этого проекта.

## Сценарии проверки

Запуск пакета из 6000 задач с одним воркером:

```powershell
uv run --locked python scripts/demo_observability.py batch
docker compose up -d --scale worker=1 worker
$batchId = [guid]::NewGuid().ToString()
$sourceContainer = docker compose run -d source python -m mlops_labs.source --input /data/batch.jsonl --batch-id $batchId
```

Во время обработки на дашборде видно, как очередь достигает лимита в десять сообщений, у источника появляются повторы и ожидание, а скорости источника и воркера сближаются. Второй воркер добавляется командой `docker compose up -d --scale worker=2 worker`. Для сравнения производительности подходят устойчивые участки длительностью не меньше минуты до и после его запуска. Переменная "Воркер" позволяет сравнить оба экземпляра. Новый `batch-id` нужен для нового независимого прогона; повтор прежнего ID проверяет идемпотентность.

Отправка задачи через API и чтение результата:

```powershell
$payload = @{recent_sales = @(10.0) * 28; day_of_week = 3; is_snap = 0} | ConvertTo-Json
$task = Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/v1/tasks -ContentType application/json -Body $payload
Invoke-RestMethod -Uri "http://localhost:8000/api/v1/tasks/$($task.task_id)"
```

Повторный GET возвращает текущий статус задачи. После успешной обработки он меняется на `COMPLETED`. Историю задачи можно найти в Grafana Explore, выбрав Loki и выполнив запрос `{service=~".+"} | json | task_id = "ID_ЗАДАЧИ"`. Поле `trace_id` открывает Tempo: ожидаемый трейс содержит `POST /api/v1/tasks`, `publish`, `process`, `inference`, `db.write_result`. Из спана доступен переход обратно к логам. Для поиска ошибок за последние 15 минут подходит запрос `{service=~".+", level=~"ERROR|CRITICAL"}` с временным диапазоном Last 15 minutes.

Повторы и DLQ на ошибке демонстрационной модели:

```powershell
$poison = @{recent_sales = (@(10.0) * 27) + @(-9999.0); day_of_week = 3; is_snap = 0} | ConvertTo-Json
$failedTask = Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/v1/tasks -ContentType application/json -Body $poison
```

Ожидаемый результат GET по `$failedTask.task_id` через несколько секунд: `FAILED`. В трейсе видны три попытки и DLQ, в Prometheus правило `TaskDeadLetters` переходит в Firing после выдержки 10 секунд.

Заполнение очереди и получение ответов 503:

```powershell
docker compose stop worker
uv run --locked python scripts/demo_observability.py api --requests 200 --concurrency 16
```

Для проверки `TaskQueueNearCapacity` воркер остаётся остановленным минимум на 75 секунд: за это время правило успевает перейти в Firing. Обработка возобновляется командой `docker compose start worker`, после чего очередь освобождается. Нагрузку API можно повторить с работающим воркером, чтобы сравнить графики 503 и латентности.

Проверка graceful shutdown: `docker compose stop worker` во время обработки пакета. В Loki при этом появляются `worker.shutdown_started`, завершение текущих задач и `worker.stopped`. Команда `docker compose start worker` запускает воркер снова.

Недоступность телеметрии можно проверить командой `docker compose --profile observability stop otel-collector`. После этого обычная задача, отправленная через API, должна завершиться со статусом `COMPLETED`. Повторный запуск Collector: `docker compose --profile observability start otel-collector`. Аналогично проверяется `stop loki` / `start loki`: конвейер продолжает обработку, а доставка сигналов ограничена буферами и сроком повторов.

Метрики RSS и in-flight используют стандартное окно актуальности Prometheus. После завершения источника или остановки экземпляра последняя точка может отображаться до пяти минут; отсутствие новых OTLP-данных само по себе не является надёжной проверкой жизнеспособности процесса.

## Трейсы и метрики

У API, источника и воркера разные `service.name`. `service.version`, `deployment.environment.name` и `service.instance.id` задаются через `OTEL_RESOURCE_ATTRIBUTES`. По умолчанию ID экземпляра берётся из hostname, поэтому реплики различимы. Заголовок `traceparent` связывает `POST /api/v1/tasks -> publish -> process -> inference / db.write_result`. Для inference контекст явно переносится в executor. Отказы и паузы источника видны в `source.backoff`, а повторные доставки представлены отдельными спанами `process` того же трейса с номером попытки. Пакет содержит отдельный трейс на каждую задачу.

На стенде `OTEL_TRACES_SAMPLER=parentbased_always_on` записывает все локально начатые трейсы и сохраняет решение родителя. Для сотен задач в секунду подойдёт `parentbased_traceidratio` с долей по замерам нагрузки. Для сохранения всех ошибок Collector с tail sampling должен получить все спаны каждого трейса и дождаться его исхода.

| Компонент | Метрики |
| --- | --- |
| API | Счётчик запросов по маршруту и коду, гистограмма длительности |
| Источник | Счётчики публикаций, nack, повторов и суммарного времени ожидания |
| Воркер | Счётчики `ok`, `error`, `dlq` и повторных доставок, текущие задачи в работе, гистограммы inference и времени до результата |
| Инфраструктура | RSS процессов из `psutil`, ready и unacked рабочей очереди, глубина DLQ |

Бакеты inference масштабируются от `INFERENCE_DELAY_MS` и при 200 мс сгущены около 180-300 мс. Для API бакеты сгущены в интервале 5-200 мс. Графики p50/p95/p99 используют `histogram_quantile` после суммирования скоростей по бакетам. Панель SLO показывает долю терминальных задач, успешно сохранённых в пределах `N`. По умолчанию `N=3 с`, целевая доля равна 99%, а error budget равен 1%. Числитель и число успешных результатов в знаменателе берутся из одной гистограммы; к знаменателю добавляются DLQ. Это исключает расхождение интервалов `increase` двух независимо начавшихся успешных счётчиков, которое могло давать более 100% после старта воркера. При отсутствии терминальных результатов панель не выдаёт фиктивные 100%. Текущий объём незавершённых задач виден по глубине очереди и in-flight.

## Оценка числа временных рядов

Оценка рассчитана для одного API, одного источника, двух воркеров и двух очередей. Число рядов равно произведению числа значений лейблов, для гистограммы оно дополнительно умножается на число бакетов и рядов суммы и количества.

Для одного API с 12 комбинациями `(method, route, status_code)` получается `12 * (1 счётчик + 9 конечных бакетов + +Inf + sum + count) = 156` рядов. Источник даёт 5 рядов, а два воркера дают `2 * (3 исхода + redelivery + in-flight + RSS + 12 рядов inference + 14 рядов времени задачи) = 64`. RSS API и две очереди добавляют 9 рядов. Итого для перечисленных метрик получается `156 + 5 + 64 + 9 = 234`, то есть около **240 рядов**. Служебные метрики и новые экземпляры увеличивают итоговое число. `task_id` добавил бы до 6000 рядов к одному счётчику или до `6000 * 12 = 72 000` к гистограмме inference.

## Алерты и бюджет памяти

| Правило | Порог | Выдержка |
| --- | --- | --- |
| `TaskQueueNearCapacity` | Средняя глубина за 10 с превышает 90% лимита. Короткое окно сглаживает освобождение отдельных слотов. | `1m`, чтобы краткое заполнение буфера не вызывало тревогу |
| `TaskDeadLetters` | В DLQ есть хотя бы одно сообщение. Каждая такая задача требует разбора. | `10s`, чтобы кратковременное появление при ручной проверке не вызывало тревогу |

Loki, Tempo и Prometheus хранят данные 2 дня. Суммарный лимит профиля наблюдаемости составляет **1440 МиБ**. Collector и Alloy тратят память на обработку и доставку, их лимиты входят в бюджет.

```powershell
$ids = docker compose --profile observability ps -q alloy loki otel-collector tempo prometheus grafana
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}' $ids
```

При проверке выполнен пакет из 6000 задач с `history-length=4096` и `INFERENCE_DELAY_MS=35`. Прогон совмещал нагрузку и проверки отказов, включая остановку и запуск воркеров. В позднем снимке `docker stats` шесть компонентов наблюдаемости использовали **566,69 МиБ**. Это отдельный замер под нагрузкой, а не непрерывно измеренный пик. [Исходный снимок и результат проверки БД](observability/verification.json) сохранены в репозитории.

| Компонент | Замер `docker stats`, МиБ | Лимит, МиБ |
| --- | ---: | ---: |
| Alloy | 59,16 | 128 |
| Loki | 70,76 | 256 |
| Collector | 40,64 | 128 |
| Tempo | 265,10 | 416 |
| Prometheus | 42,65 | 256 |
| Grafana | 88,38 | 256 |
| **Всего** | **566,69** | **1440** |

Лимит 1440 МиБ относится к стеку наблюдаемости; сервисы конвейера в него не входят. PostgreSQL подтвердил 6000 уникальных задач пакета, все в состоянии `COMPLETED`, по одной попытке на задачу. Этот смешанный прогон не доказывает линейный рост скорости при добавлении второго воркера: для сравнения нужны отдельные устойчивые окна при одинаковой нагрузке и после прогрева.

Отдельный замер масштабирования выполнен с `INFERENCE_DELAY_MS=200`, `history-length=28`, лимитом очереди 10, `prefetch=1` и 1600 задачами. В каждом устойчивом участке после прогрева использовано окно `rate(...[1m])`; менялось только число воркеров.

| Воркеры | Публикации источника, задач/с | Обработка, задач/с |
| --- | ---: | ---: |
| 1 | 4,26 | 4,40 |
| 2 | 8,57 | 8,59 |

Рост обработки составил **1,95 раза**, скорость источника приблизилась к суммарной скорости воркеров. БД подтвердила 1600 уникальных `COMPLETED`, по одной попытке; источник завершился с кодом 0. Исходные ответы Prometheus и итог БД находятся в `controlled_scaling` файла [verification.json](observability/verification.json). Это измерение демонстрационной модели с заданной задержкой, а не оценка производительности модели M5.
